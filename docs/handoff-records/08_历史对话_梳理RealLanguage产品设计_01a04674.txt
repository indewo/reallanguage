1. **产品定位**  
   RealLanguage 面向已有一定英语基础、但难以把真实想法自然准确地用英语表达的成年人。核心是把用户自己的中文内容练成能够完整写出、完整复述，并把重点表达迁移到其他合适场景中；它不是覆盖所有英语能力的综合课程。

2. **三个内容入口**  
   日记、录音、AI 设定场景。三条路径独立保存来源、固定内容、场景、章节和学习进度，不合并内容。

3. **普通学习、回顾和知识本的关系**  
   普通学习始终沿三条独立路径进行。完成三个实际普通学习日后进入统一回顾，三个来源的待复习重点句进入同一队列，但每项仍回到自己的原句、原章节和原场景。

## 建议纳入 MVP

### 1. 基础产品框架

- 手机横屏信息架构；
- 首次设置，后续直接进入首页；
- 常驻设置入口及设置变更生效范围选择；
- 日记、录音、AI 设定场景三个独立入口；
- 固定内容、未完成队列和章节进度保存。

### 2. 三个内容入口

- 日记输入、语义拆分、全量展示和重点句选择；
- 录音、转写、手动编辑及用户主动触发的 AI 优化；
- AI 场景的近期推荐、8 个公共模板和直接描述；
- AI 场景区分对话与文章，以 1—5 个问题形成短内容；
- 中文内容编辑与宽松 AI 审核；
- 三个入口统一选择1—3个重点句、提取3—4句上下文并分章。

### 3. 内容固定

- 只为学习章节生成英文；
- 严格原意保真；
- 唯一合格英文自动采用，多个同等合格表达才供选择；
- 目标词义、短语和句式默认选中并允许反选；
- 用户确认后锁定本次固定内容和验证目标。

### 4. 完整学习闭环

每章包含：

- 首次讲解与三轮增量朗读；
- 读＋说；
- 两次手写抄写及识别反馈；
- 音频听写与错误订正；
- 整句会说；
- 有支持的句式会说；
- 完整书写；
- 场景回应；
- 章节结果、错题和未完成项归档；
- 用户主动确认是否进入下一章。

### 5. 共享知识与回顾

- 独立词汇本；
- 独立句式本；
- 句子本地状态与共享知识状态隔离；
- 词义多义分行及具体能力状态；
- 三个普通学习日后的统一回顾；
- 每个回顾自然日最多完整处理3个重点句；
- 下一次普通学习最多先补1个未完成重点句；
- AI 场景优先承担旧知识的自然复现。

### 6. MVP 必须满足的底线

- 三个入口的来源和学习进度不合并；
- 非重点句只提供语境，不建立主动任务；
- 未保存内容不建立草稿或放弃状态；
- 没有正式判断的退出不记为失败；
- 非目标知识不因偶然出现而更新状态；
- 所有反馈客观说明结果、依据和下一步；
- 关闭语音后，全部流程仍能通过文字完成；
- 测试中的“下一步”“假设完成”“跳过”不成为产品能力。

## 建议不纳入 MVP

这些内容不是被否定，而是建议延期：

- 多平台同时发布；
- 跨设备同步；
- 社交、排行榜、打卡和社区；
- 完整考试课程或通用英语课程；
- 自动推测长期人格或 Expression Profile；
- 大量公共标准课程和标准答案；
- 多套角色声线或复杂声音市场；
- 高级运营后台；
- 复杂订阅、退款和商业化体系；
- 精细化推荐算法实验；
- 不影响核心闭环的动画和装饰性视觉效果。

## 仍需确认的关键范围

1. **MVP 性质**  
   是内部可操作原型、封闭内测产品，还是可公开下载的首发版本？我目前建议按“封闭内测产品”定义。

2. **三个入口是否必须同时首发**

3. **是否完整保留全部学习模块**  
   我建议先保留，因为当前状态和回顾规则依赖完整闭环；如果需要缩减，应明确删减对验证结果和知识状态的影响，不能简单隐藏页面。

4. **账户与数据范围**  
   当前尚未确定是否需要账户、云端同步和换机恢复。建议 MVP 先支持单设备使用，但固定学习数据必须可靠持久化。

5. **录音保存范围**  
   已确认原始录音长期保存在手机本地并可单独清理。需要确认这是否属于 MVP 必做，还是首发仅保存转写及固定学习内容。

6. **首发设备与系统**  
   需要确定 iPhone、Android 或两者；这会直接影响横屏、录音、手写识别和语音能力的实现范围。

因为用户放弃时，可能已经：

- 完成了前面章节；
- 产生了整句、词义或句式的正式验证结果；
- 将词义或句式共享给其他学习内容；
- 让该内容成为知识本的代表场景；
- 产生了AI费用和消费记录。

建议定义为：

> 用户可以放弃一份固定学习内容。确认后，删除该来源对应的全部章节、固定句、句子状态和未完成任务，并从回顾、近期推荐及学习记录中移除。

同时必须遵守：

- 只撤销由这份内容独立产生的学习证据；
- 其他内容也使用的词义或句式不能一起删除；
- 共享知识状态根据剩余有效记录重新计算；
- 代表场景来自被删除内容时，需要换成其他有效场景；没有其他来源时才移除；
- 充值、扣费、退款和安全审核记录不能作为学习资料展示，但必须按财务、安全规则保留；
- 操作不可恢复，需要二次确认。

因此，这项功能合理，但实现成本不低，会让数据模型增加“删除来源后重新计算共享知识”的能力。

## 3. 学完后删除句式本内容

如果你说的“结构本”是“句式本”，**允许用户整理自己的句式本是合理的**，但建议按钮叫：

> `移出句式本`

而不是模糊的“删除”。

移出后：

- 不再安排该句式的主动学习、验证、回顾和自然复现；
- 删除该句式的代表场景与3个例句；
- 原来已经完成的固定句不改变；
- 不影响完整句子的会写、会说和场景回应结果；
- 如果以后用户在新内容中再次明确选择这个句式，应作为新学习项重新建立状态。

## 审查结论

- 固定前换模板：**直接采用**；
- 学习中放弃并删除整份内容：**合理，但必须增加共享状态回算规则**；
- 学完后删除句式本内容：**合理，建议定义为“移出句式本”**。

我建议下一步先确认最关键的一点：放弃学习时，你希望删除的是**当前章节**，还是这份来源形成的**全部章节和整份固定学习内容**？

有一处需要修正：不能简单写成“上层依赖下层”。

合理的执行调用链是：

```text
Page
→ API Route / Controller
→ Application Use Case
→ Domain Service
→ Repository Interface
→ Repository Implementation
→ Database
```

但代码依赖方向应是：

```text
Presentation → Application → Domain
Infrastructure → Application / Domain 的接口
Domain → 不依赖其他层
```

也就是说，数据库实现反过来依赖业务层定义的 Repository 接口。业务领域层不能依赖 PostgreSQL、Redis、供应商 SDK 或 HTTP 框架，否则以后更换数据库或供应商仍会牵动核心业务。

建议在 v0.2 补齐以下内容：

1. **标准四层与依赖规则**

   每个业务模块内部固定为：

   ```text
   presentation/
   application/
   domain/
   infrastructure/
   ```

   禁止 Route 直接访问 Repository，禁止 Domain 引用数据库、HTTP、队列或供应商 SDK。

2. **DDD 模块所有权**

   使用 RealLanguage 自己的领域模块：`learning`、`review`、`billing`、`safety`、`knowledge` 等。每个模块拥有自己的实体、数据写入和公开接口；禁止跨模块引用内部类、Repository 或直接修改对方表。

3. **接口与实现分离**

   Repository、AI、支付、通知、时间、文件等都先定义接口，再由基础设施层提供实现；统一在 Composition Root 完成装配。

4. **突发流量机制**

   API 无状态并可横向扩容；不同 AI 任务使用独立队列；Worker 可独立扩容；设置队列上限、背压、用户限流、供应商并发限制、超载降级及 `Retry-After`。

5. **完整容错**

   为外部调用定义超时、有限重试、指数退避加随机抖动、熔断、舱壁隔离、死信队列、人工重放和降级边界。

6. **并发与消息语义**

   明确事务边界、数据库隔离级别、任务领取方式、同一内容的顺序控制，以及“至少一次投递＋业务幂等”，不承诺无法保证的绝对只执行一次。

7. **API 契约治理**

   使用 OpenAPI；统一请求、响应、错误、分页和请求 ID；定义兼容性、弃用周期和客户端最低支持版本。

8. **测试驱动开发**

   固定顺序：

   ```text
   定义接口/验收条件
   → 编写失败测试
   → 最小实现
   → 测试通过
   → 重构
   → 再进入下一功能
   ```

   同时规定单元、领域、Repository 集成、API 合同、模块合同、端到端、并发、故障注入和负载测试。

9. **测试数据隔离**

   每次测试使用独立事务或独立数据库命名空间；禁止依赖执行顺序；外部供应商使用可控 Fake；生产密钥和生产数据禁止进入测试。

10. **可观测性与发布安全**

    统一结构化日志和错误分类；请求 ID、operation ID、任务 ID 跨 API/队列/Worker 传递；补充健康检查、优雅停机、数据库迁移、回滚、Feature Flag、SLO、告警等级和排障手册。

这十项补完后，架构才真正具备“可扩展、可维护、可定位、抗故障，并且能约束 AI 编码不乱长”的能力。下一步应直接把它们写入 `ARCHITECTURE.md` v0.2，再让你确认。
